# COG-20: Agent Admission

```
Status:      Draft
Version:     0.1
Created:     2026-08-30
Updated:     2026-10-29
Authors:     Mike Anderson
```

:::note Related specifications
This standard adds one admission class to the access rules for hosted agents in
[COG-14 §4](./COG-014#4-access-control) — a target-side policy the agent's
owner declares on the record — alongside the existing owner, capability
([COG-13](./COG-013)) and public-exposure
([COG-14 §5](./COG-014#5-granting-public-or-delegated-access)) classes. It
introduces no new token, no new authority primitive and no change to execution
identity: it decides only whether a principal may *talk to* an agent without
presenting a delegation.
:::

Agents need to converse and delegate across users — an operator's
administrative agent taking requests from a resident's assistant, two users'
assistants corresponding. Capability delegation
([COG-13](./COG-013)) covers this in principle, but for the common standing
arrangement it is the wrong tool: the *caller* must hold and present a token
for every target, and an agent holds none. The natural authority is the target
owner's: "these principals may talk to my agent." This standard lets the owner
say so once, on the record, and has the venue honour it at the same point where
it would otherwise look for a delegation.

## Principles

- **The target decides.** Admission is the target owner's standing policy on
  the target's record. Callers present nothing.
- **Exact, never inferred.** An allowlist names principals by DID and matches
  them exactly. No prefixes, no families: a user is not its agents, and an
  agent is not its owner.
- **The operator is a class of one.** "The venue" means the venue operator —
  the venue principal and the agents it owns — and is clearly distinguished
  from every other user the venue hosts. "Everyone on this venue" is not a
  class.
- **Talking only.** Admission covers submitting requests and messages. Reading
  an agent, changing it or controlling it still requires a delegation.
- **Anonymous stays elsewhere.** The venue's public principal is never
  admitted; anonymous exposure remains the public lever of
  [COG-14 §5](./COG-014#5-granting-public-or-delegated-access).
- **Provenance, not instruction.** The admitted caller is recorded as the
  initiator and shown to the agent as venue-verified fact — never as a claim
  inside the request.

## Specification

### 1. The admission policy

An agent record MAY carry an admission policy, `accepts`, in its
configuration. Its value is one of:

| Value | Admits |
|-------|--------|
| `"owner"` (default when absent) | nobody beyond the owner; other callers need a delegation |
| `"venue"` | the venue operator: principals whose user is the venue's own DID — the venue acting directly, and agents it owns |
| an array of principal DIDs | exactly those principals: a user DID admits that user only; an agent DID (`<userDID>:g:<agentId>`, [COG-13](./COG-013)) admits that one agent only. The keyword `"venue"` MAY appear as an entry |

Any other value is malformed. A venue MUST reject a malformed policy when the
record is created or updated, and MUST treat a malformed policy it nevertheless
holds as admitting nobody.

### 2. What admission covers

Admission applies to the abilities that mean "talk to this agent" — submitting
a request or a message (`agent/request` and `agent/message` in the ability
vocabulary of [COG-13](./COG-013)) — and to the agent record as the resource,
`<ownerDID>/g/<agentId>`. It MUST NOT extend to any other ability on that
resource (reading, writing, forking, control), nor to any path beneath it (the
agent's workspace or sessions).

### 3. Evaluation

When a principal other than the owner addresses an agent, the venue evaluates
admission at the same point at which — and before — it evaluates presented
delegations ([COG-13](./COG-013)); the two are alternatives, and either
suffices. A caller that is the venue's public (anonymous) principal is never
admitted by policy, whatever the policy says.

Matching is exact on the caller's acting principal DID. For `"venue"`, the test
is whether the caller's *user* — the owner for an agent principal, the principal
itself otherwise — is the venue's own DID (or its `did:web` alias).

### 4. Execution and provenance

Admission changes nothing about execution identity: the agent runs as its own
sub-principal within its owner's namespace ([COG-13](./COG-013)), and the
request or message remains the caller's own unit of work. The venue MUST record
the caller as the initiator on that unit of work, and MUST present it to the
agent as venue-verified provenance — the caller's user, its agent id if it is
an agent, and its venue where known — distinct from the request content.

### 5. Denial

A caller that is neither the owner, admitted, nor delegated is denied exactly
as [COG-14 §4](./COG-014#4-access-control) prescribes. The denial SHOULD say
that the target's admission policy does not admit the caller.

## Out of scope

- Agents holding and presenting delegations of their own — the general
  mechanism that admission short-cuts.
- Cross-venue addressing of agents ([COG-15](./COG-015)).
- Admission on other per-user resources, such as a human-in-the-loop inbox
  ([COG-16](./COG-016)).
